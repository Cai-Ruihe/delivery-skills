# Changes

## delivery-skills-2026-10-10-r1

This revision replaces and consolidates existing guidance across the same six entries and nine references. It adds no runtime file, role, reporting service or approval layer.

1. Progress means an advance in the requested capability or evidence that changes a critical decision. The execution loop selects the first unproved real dependency, with proportionate risk, reversibility and lifecycle cost. Necessary preparation and lawful architecture pauses remain valid partial work.
2. PM owns the integrated executable version, useful parallel dispatch, result consumption and honest milestones. Implementation needs a receivable contract and integration capacity; bounded investigation may establish an unknown interface. Final acceptance checks the actual entry, package/runtime and known correction together before claiming consumer success.
3. Contact guidance distinguishes a draft, transport acceptance, acknowledgment, consent and result. Plan a realistic decision opportunity, disclose current execution gaps and never count unverified delivery or reply wall time as net project delay. Unknown delivery does not authorize automatic resend; late consent does not revive expired authority.
4. Architect keeps independent high-level judgment. Its entry now points to the existing architecture method instead of repeating it; the method itself is unchanged. Advice needs reasoned PM disposition, not routine architectural approval or Architect ownership of integration.
5. Important recurrence without a changed critical premise or real-boundary advance prompts a route decision: a discriminating hypothesis, a narrower next milestone preserving the agreed outcome, an evidence-led route change, or a precise escalation. The original five-failure repair backstop and stricter limits remain; the backstop does not authorize five attempts.
6. Reflection reuses one changed-evidence record. User-required three-hour independent Architect reviews, including HOLD, are preserved. Checkpoint, admission closure, actual pause and cleanup evidence stay distinct; no unsupported wakeup is promised. Conditional navigation and unchanged-context reuse do not eliminate necessary refresh after context loss.
7. Recurring resource responsibility uses an existing authoritative resource record or native task/run state: owner, purpose, authorized spend/time basis, review/end condition and disposition. Development stop is not billing stop. Estimates are not invoices; unchanged grants need no repetitive approval, and missing shutdown authority requires the smallest actual decision.

Existing authority, tool-retry, uncertain-result, temporary-operation, stop and cleanup mechanics remain in their original references. No whole-operation lifecycle, new readiness gate or independent cleanup qualification is introduced. This revision does not claim to resolve every execution-readiness gap.

All fifteen runtime documents and all six UI configurations match the reviewed installed unit exactly. The core README differs only in its source-stage/release paragraph; this does not change runtime rules. The public README and loading/change notes describe this release. MIT notices, model defaults and role policies are preserved.

Static validation and independent semantic review are complete. They establish structure and reviewed content, not PM autonomy, actual loading, consumer success, lower cloud cost or faster delivery. Model behavior trials have not been run. Cold-path costs and conditional navigation cycles are disclosed in [context loading](context-loading.md).

## delivery-skills-2026-10-04

This release reorganizes rule ownership and execution rather than appending a second workflow.

1. Shared philosophy distinguishes values, revisable empirical defaults and procedures; unfamiliar cases use explicit intent, evidence and reversible checks.
2. One execution loop supports PM autonomy: observe the current boundary, choose a useful action, act, integrate and verify. Bounded research must change the next decision or expose a precise gap, then return to delivery.
3. Architect forms an independent high-level view and returns executable trade-offs. Root-cause diagnosis compares local repair, boundary consolidation and mechanism replacement; elegance is not fewer lines or more abstraction. Emergency patches have observable repayment triggers.
4. The smallest real end-to-end slice checks risky runtime/access/reader boundaries early. Worker or local PASS proves only its actual scope; fixtures do not establish a real consumer outcome.
5. Parallel work requires independent contracts, isolated write surfaces and accountable integration. Zero workers is valid; coupled uncertainties stay with one owner.
6. Existing grants are reused for ordinary authorized actions. Official provenance does not expand permission. Old messages, busy writers, unknown operations and lawful stops are reconciled without automatic duplicate effects or resumption.
7. Short entries navigate conditional references. The old PM cycle and other superseded references are retired, leaving one body per shared rule. Reflection checks whether the previous correction changed the next action rather than producing another essay.

## Validation and limits

The runtime unit contains six entries and nine references, with six UI configurations and three core auxiliary files. MIT notices are retained. Default orchestrator/worker profiles and existing specialized role invocation settings remain subject to user and host policy.

Structural validation, local links, reference cycles, size, sanitization and final byte consistency are mechanical evidence. They are not model behavior trials. No efficiency, autonomy or quality improvement has been measured here. The repository has no private retrospective, research workspace, real case records, source mapping, backup or evaluator oracle.
